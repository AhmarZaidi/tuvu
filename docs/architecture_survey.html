Tuvu Architectural Survey

A comprehensive technical deep-dive into the Tuvu web application, mapping infrastructure, data flows, and the Phase 7.5 refactor trajectory.

Overview & Hosting setup

Deployment Architecture

Tuvu is designed as a fast, cost-effective personal media tracker tailored for Cloudflare Workers.

  • Client: Vite-built React Single Page App (SPA).
  • API: Hono routing framework deployed on Cloudflare Workers.
  • Database: Cloudflare D1 (Serverless SQLite).
  • Asset Delivery: Cloudflare Static Assets (run-worker-first configuration for /api/*).

Hosting Limitations

The architecture is intentionally bounded by Free-tier limits:

  • Cloudflare D1: SQLite limits apply. Heavy aggregations (dashboard stats) must not be computed per-request.
  • Supabase Storage: Free tier limits to 1 GB storage and 5 GB egress. File limits are capped (50MB total, but Avatars bounded to ~2MB, Banners ~5MB). Media caches must be easily evictable.
  • Workers Execution: External API hydration must be asynchronous (ctx.waitUntil) to avoid exceeding request timeouts or blocking UI.

The client leverages React Query / Zustand for UI state and cache, fetching from the Hono Worker. The worker validates Auth (Passkeys/OAuth via session cookies), retrieves data from D1, and proxies/hydrates missing metadata from External APIs (TMDB, RAWG, etc.) using a Stale-While-Revalidate caching pattern.

Internal Hono Endpoints (Worker)

  • /api/auth/* - Passkey / OAuth / Session handling.
  • /api/media/* - Detail retrieval, episode guides, unit tracking, cover uploads.
  • /api/library/* - User mutations (add/remove, rating, status). 7.5 moves stats calculation away from here to a batch snapshot service.
  • /api/explore/* - Search bridging local DB and Provider Caches.
  • /api/import/* - TV Time ZIP/CSV uploads, chunk processing, commits, and rollbacks.
  • /api/merge/* - Alias resolution for manually created/imported items vs canonical provider items.

Data Strategy & Flows

1. The Search & Add Flow

The app prioritizes local database speed, falling back to providers.

  1. Client hits /api/explore/search.
  2. Worker searches local D1 canonical media first.
  3. If debounced and user-triggered, hits Provider Caches, then External Providers.
  4. User adds item: Worker creates a lightweight global canonical row (if it didn't exist) and attaches a user-scoped library row.
  5. Async hydration job is queued to fetch heavy metadata (episodes, credits) in the background.

2. Import & Merge Flow

Designed to handle incomplete metadata from TV Time exports.

  • Parse: Client parses CSV/ZIP locally via Papa Parse.
  • Chunking: Worker commits in bounded batches to avoid D1 timeouts.
  • Placeholders: Creates local canonical placeholders for imported items.
  • Merge: The Merge UI allows users to resolve placeholders against real Provider IDs, migrating tracking data and queueing hydration.

3. Manual Data & Authorization

Users can bypass providers for niche items.

  • Users can manually create media if search fails.
  • Creates a media_source_records entry mapping to a canonical ID.
  • Auth Strategy: All mutation routes require valid HTTP-only cookies validated via auth-repository.
  • Future Social: Placeholder tables exist for Comments & Reactions.

Caching & Loading Strategies

Server-Side Strategy

Stale-While-Revalidate
  • provider_cache: Saves raw provider JSON to bypass rate limits (429s).
  • media_metadata_freshness: Tracks detail/episode hydration expiry.
  • If a media page is requested and metadata is stale, the Worker returns the cached D1 data immediately and uses ctx.waitUntil to trigger a background refresh.

Client-Side Strategy

Version-Based Invalidation
  • Phase 7.5 Query Cache: Moving away from ad-hoc maps to a formal query cache (api/query-cache.ts).
  • Library Versions: Each user mutation bumps a user_library_versions.version in D1.
  • Client checks version on window focus or mutation return; if bumped, it invalidates local caches (Dashboards, Detail pages) ensuring cross-device sync.

UI Loading & Notices

Loading states rely entirely on client-side rendering logic.

  • Skeletons: SkeletonGrid and inline skeletons used while React Query fetches data.
  • Global Snackbar: Dedupes identical error/success notices, replacing page-local Toast components (7.5 refactor).
  • Job Banners: Persistent JobProgressBanner used for long-running imports/merges instead of ephemeral toasts.

Codebase Mapping & 7.5 Optimization

The "Monolith" Problem (Pre-7.5)

The app developed rapid feature bloat resulting in significant duplication:

  • Client Monolith: src/client/app.tsx contains Routing, App Shell, Fetching, Dashboard logic, and Media detail layouts.
  • CSS Drift: src/client/styles.css has hard-coded colors and duplicate light/system theme rules.
  • Worker Monolith: media-repository.ts handles catalog, library, dashboard count SQL, and activity.
  • Ad-Hoc Stats: Dashboard counts (Shows vs Anime) are recalculated dynamically on every request.

Phase 7.5 Restructuring Plan

The codebase is actively being fragmented into highly cohesive domain modules.

1. Shared Domain Definitions

Media types (Shows, Anime, Books, Games, Movies) are centralized into a MediaTypeConfig registry to prevent scattered `if/switch` statements across client & API.

2. Client Architecture (Design System)

Moving to features/ (auth, profile, library), design/ (tokens, UI components like Button, Sheet, Snackbar), and shell/. CSS is moving to CSS Variables (Tokens) to easily support future themes and compactness settings.

3. Worker Architecture (Services/Repos)

Routes validate input. Services (media-canonical-service, stats-service, hydration-service) own orchestration. Repositories own SQL. Provider fetches are isolated into tmdb.ts, rawg.ts, etc.

4. Batched Stats

Moving away from real-time paginated counts. Import/Merge flows now trigger a batched recalculation saved to user_stats_snapshots.
